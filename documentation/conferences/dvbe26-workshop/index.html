/onboarding


Makes the repository ready to work with Plinth AI native workflow
by securing two prerequisites:

Root AGENTS.md
Repository-specific instructions for the coding agent
Interactive: asks 6 questions, one by one
  1. Role · backend, full-stack, DevOps, architecture…
  2. Tech stack · Java version, build tool, frameworks
  3. File structure · read-only vs. editable folders
  4. Commands · build, test, run
  5. Git workflow · commit style, PR checklist
  6. Boundaries · always, ask first, never
Init OpenSpec project
Creates OpenSpec project structure by running openspec init

* Only needs to be done once per repository / project.

Go 1x on the spec 10x on the code

1x · Design
Invest quality time gathering and refining the requirements
10x · Implementation
Safe to accelerate: intent, constraints and verification path are already defined

Why the separation and order matters

Two artifacts, two questions, two audiences

Functional Specification
What the system must do, and why
approved by the business
Technical Specification
How to build and verify it
approved by engineering
Decide the how first and it silently becomes the what

/update-issue


Rewrites an existing issue description as structured, evidence-backed content

Input
  • GitHub or Jira issue number, key or URL
  • Optional source: notes, discussion, user story, file path
  • Current issue body and discussion are read first
Output
  • Structured user story in the issue description
  • Acceptance criteria or scenarios when applicable
  • Updated issue reference and URL

/explore-problem


Evaluates the issue through five lenses and produces a Functional Specification

Problem framing
Problem statement, current and desired state, stakeholders, success criteria
Root cause
Five Whys, Fishbone, Current Reality Tree, constraints
Assumptions
Assumptions, unknowns, validation plan
Context mapping
Existing systems, integrations, ownership, external dependencies
Quality attributes
Discover and prioritise what the solution must satisfy
Each lens asks clarifying questions when its content is vague

/create-acceptance-criteria


Turns the Functional Specification into observable Gherkin scenarios

Input
The Functional Specification resulted from /explore-problem
Output
# Acceptance Criteria
Feature: <name>
  Scenario: <observable>
    Given <context>
    When <event>
    Then <outcome>

turns what and why into something checkable and easier to review

What is OpenSpec?

A lightweight and configurable framework for creating and managing software specifications.

Build the right thing, and build it right

Capture what you want to build in a spec, and keep your team and your coding agents aligned as the work evolves.

Refine
the requirements
Validate
that they describe the right thing
Verify
that the implementation matches
Plinth orchestrates spec implementation by reusing OpenSpec primitives

/create-spec


Turns approved material into a validated OpenSpec change

Input
  • Issue or user story with its acceptance criteria
  • Approved design, ADRs or implementation plan
  • An existing OpenSpec change to update
Output
  • Proposal, design, specs and task list
  • Requirements as Given / When / Then scenarios
  • Validation and traceability report

/explore-design


Refine the technical design of an issue or OpenSpec change before implementation.

Input
  • OpenSpec change with an unresolved approach
  • Architecture context and constraints
Output
  • Alternatives, trade-offs and rejected options
  • Recommended direction with rationale
  • Components, data flow, failure handling, testing strategy
  • ADR candidates and open questions
  • A recommendation is not a decision: nothing is approved until a human confirms it

ADR · Architecture Decision Record: a short document capturing one decision, its context and its consequences.

/create-adr


Records an architectural decision that has already been taken

Input
  • Approved design, issue, spec or plan
  • Existing constraints and related ADRs
  • Optional type: general, functional, non-functional
Output
  • One ADR following the repository convention
  • Status, rationale, alternatives, consequences
  • Links to the source artifacts

/create-diagram


Draws one architecture view from the approved artifacts

Input
  • Issue, design, ADR, spec or repository architecture
  • Optional type: sequence, class, state machine, ER, C4
  • Audience and level of detail
Output
  • Diagram source for that single view
  • Scope and assumptions made
  • Links to the artifacts represented

/implement-spec


Delivers an approved task list through framework-aware delegation

Input
  • Validated OpenSpec change or approved plan
  • Acceptance criteria and testing strategy
  • Repository conventions and build commands
Output
  • Code and tests for each completed task
  • Build and test run as evidence
  • Delegation does not transfer accountability: the diff is still reviewed by a human

/implement-spec

The tech lead agent runs the process, but it never writes code itself

1 · Gate
Is the spec ready?
  • Change is current, approved and consistent
  • Every scenario has a task, and every task a scenario
  • Workspace is clean
→
2 · Route
Where, and by whom?
  • Feature branch or worktree (main only with explicit approval)
  • Coder matched to the framework: Spring Boot, Quarkus, Micronaut, Java or non-Java
  • Relevant skills picked for that coder
→
3 · Delegate
Who builds what?
  • Tasks split into groups, each owning its files
  • Dependent groups run in order; independent ones run in parallel
  • Each handoff: tasks, acceptance criteria, checks to run
→
4 · Verify
Is it really done?
  • Coder returns changed files, test and build results
  • Task marked done only when its acceptance criteria pass
  • Blockers and risks reported
✗ If any check fails, it stops and reports. Nothing is guessed, bypassed or invented.

/close-spec


Archives a delivered OpenSpec change and folds it into the specs

Input
  • OpenSpece change whose tasks are complete
  • Evidence that acceptance criteria are met
Output
  • Change archived through the OpenSpec CLI
  • Specs updated to reflect the new behaviour
  • A clean slate for the next change
